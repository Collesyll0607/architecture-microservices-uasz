Introduction

Ce document présente le travail réalisé dans le cadre du devoir du module Développement d'Applications Orientées Services en Licence 3 Ingénierie Informatique (L2I). L'objectif du sujet est de construire une application distribuée reposant sur une architecture microservices pour gérer et valoriser les sites patrimoniaux, les circuits touristiques, les événements culturels et les réservations de visites dans la commune de Ziguinchor et en Basse-Casamance.

Le travail demandé s'appuie sur l'enchaînement des trois fiches de travaux pratiques vues en cours : la mise en place de la couche de persistance avec Spring Data JPA (TP 1), l'encapsulation des échanges par objets de transfert (DTO), le mapping automatique avec MapStruct et la communication synchrone inter-services via Spring Cloud OpenFeign (TP 2), puis la conteneurisation de l'ensemble des services et de l'interface cliente sous Docker et Docker Compose (TP 3).

1. Architecture générale de l'application

1.1. Découpage en microservices

Plutôt que de regrouper l'ensemble des traitements dans une seule archive monolithique, le domaine métier a été réparti en quatre microservices Spring Boot distincts et une application cliente Angular. Chaque service gère son propre périmètre fonctionnel et expose une API REST consommée en JSON.

Composant Port Responsabilité fonctionnelle Socle technique
ms-patrimoine 8081 Gestion du référentiel des sites patrimoniaux (localisation GPS, historique, capacité). Spring Boot 3, Spring Data JPA, MySQL
ms-circuit 8082 Gestion des circuits touristiques, des étapes ordonnées et récupération des sites via OpenFeign. Spring Boot 3, OpenFeign, MapStruct
ms-evenement 8083 Programmation des événements culturels, gestion du nombre de places et des tarifs. Spring Boot 3, Spring Data JPA, MySQL
ms-reservation 8084 Enregistrement des réservations, génération du pass QR et suivi des paiements. Spring Boot 3, Spring Data JPA, MySQL
frontend-angular 4200 Interface web destinée aux trois profils : Touriste, Guide et Conservateur. Angular 17, TypeScript, Bootstrap 5

1.2. Base de données et persistance (TP 1)

Les données sont stockées dans le schéma MySQL patrimoinedb encodé en utf8mb4. Dans chaque microservice, les classes entités sont annotées avec @Entity et manipulées à travers des interfaces héritant de JpaRepository. Ce choix permet de déléguer à Hibernate la génération des requêtes SQL standards ainsi que la gestion des transactions.

2. Structuration par DTO, MapStruct et OpenFeign (TP 2)

2.1. Séparation entre entités JPA et objets de transfert (DTO)

Exposer directement les entités JPA sur les contrôleurs REST pose deux problèmes classiques : le couplage de l'API publique au schéma physique des tables et les erreurs de sérialisation cyclique sur les relations bidirectionnelles (notamment entre Circuit et EtapeCircuit). Pour éviter cela, chaque microservice utilise des classes DTO dédiées et un mapper MapStruct compilé.

Extrait 1 : Interface de mapping MapStruct dans ms-circuit (CircuitMapper.java)
@Mapper(componentModel = "spring")
public interface CircuitMapper {
    CircuitDTO toDTO(Circuit entity);
    Circuit toEntity(CircuitDTO dto);

    EtapeCircuitDTO toEtapeDTO(EtapeCircuit entity);
    EtapeCircuit toEtapeEntity(EtapeCircuitDTO dto);
}

2.2. Communication inter-services avec Spring Cloud OpenFeign

Un circuit touristique est composé d'une suite d'étapes faisant chacune référence à un site patrimonial par son identifiant (patrimoineId). Lorsqu'un utilisateur consulte un circuit sur ms-circuit (port 8082), ce service interroge ms-patrimoine (port 8081) via le client déclaratif PatrimoineFeignClient afin de compléter chaque étape avec les informations du site correspondant.

Extrait 2 : Client déclaratif OpenFeign (PatrimoineFeignClient.java)
@FeignClient(name = "ms-patrimoine", url = "${ms.patrimoine.url:http://localhost:8081}")
public interface PatrimoineFeignClient {

    @GetMapping("/api/patrimoines/{id}")
    PatrimoineDTO getPatrimoineById(@PathVariable("id") Long id);

    @GetMapping("/api/patrimoines")
    List<PatrimoineDTO> getAllPatrimoines();
}

3. Conteneurisation et déploiement avec Docker (TP 3)

Conformément aux consignes du TP 3, chaque microservice possède son fichier Dockerfile basé sur l'image eclipse-temurin:21-jdk. Le client Angular est compilé puis servi par un conteneur Nginx (nginx:alpine) qui assure également le routage des requêtes /api/* vers les microservices concernés. L'orchestration globale est décrite dans le fichier docker-compose.yml à la racine du projet.

Extrait 3 : Déclaration des services dans docker-compose.yml
services:
  ms-patrimoine:
    build: ./ms-patrimoine
    image: collesyll/patrimoines:v1
    ports: ["8081:8081"]

  ms-circuit:
    build: ./ms-circuit
    image: collesyll/circuits:v1
    ports: ["8082:8082"]
    environment:
      - MS_PATRIMOINE_URL=http://ms-patrimoine:8081
    depends_on: [ms-patrimoine]

4.2. Espace Touriste et Tableau de bord du Conservateur

Les droits d'accès sont différenciés selon le rôle de l'utilisateur connecté :

- Le Touriste : dispose d'un espace dédié (Figure 3) regroupant ses réservations, son billet numérique avec QR Code (vérifiable hors-ligne par le guide), le règlement par Wave ou Orange Money, ainsi que la possibilité de déposer un avis ou de signaler un litige à l'issue d'une visite.

- Le Guide : consulte uniquement son planning de créneaux horaires et la liste des visites qui lui ont été assignées, avec la possibilité de marquer une visite comme terminée.

- Le Conservateur : accède au tableau de bord d'administration (Figure 4) lui permettant de superviser les effectifs, de valider les candidatures de guides, de planifier une visite en sélectionnant un site et un guide habilité, de traiter les litiges et de suspendre un compte utilisateur en cas de manquement.

Figure 3 : Espace Touriste — suivi des réservations, pass QR et médiation.
Figure 4 : Tableau de bord du Conservateur — indicateurs et planification des visites.

Conclusion

Ce devoir nous a permis de mettre en pratique l'ensemble de la chaîne de conception d'une application orientée services : modélisation des entités JPA, isolation de la couche d'exposition par DTO et MapStruct, appels synchrones inter-services avec OpenFeign et déploiement multi-conteneurs sous Docker. Le découpage retenu facilite la maintenance de chaque brique tout en offrant une interface cohérente aux différents acteurs du tourisme local.
